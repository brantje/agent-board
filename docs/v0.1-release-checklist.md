# v0.1 release checklist

Issue #18 is the v0.1 release gate. Release evidence must prove the normal Runner-first lifecycle rather than only individual subsystem tests.

## Automated gates

- `go test`, coverage, `go vet`, and `go build` remain green for the server, `agent-runner`, and shared Runner protocol packages.
- Frontend typecheck, coverage, and build remain green.
- The scripted external Runner walking skeleton registers the real standalone `agent-runner` with a one-time registration token, starts it from persisted Runner configuration, exercises scheduler-owned placement and Workspace transfer/sync-back, and verifies Runner capacity is released again.
- Existing Docker Runtime/Runtime Instance integration tests remain green as legacy/internal managed-compute regression coverage.
- `.github/workflows/opencode-integration.yml` runs the existing credential-gated OpenCode/OpenRouter scenarios plus `TestOpenCodeExternalRunnerGoldenPath` using an explicitly allowlisted OpenRouter model.
- The external OpenCode golden path proves a deterministic fixture fails before execution, runs on the expected standalone external Runner without a Runtime Instance, reaches `READY_FOR_REVIEW`, leaves the authoritative Project repository unchanged before approval, approves through the normal Review application service, reaches Review `APPROVED` / Run `COMPLETED` / Issue `DONE`, changes only the expected implementation file, and passes the fixture's real tests in the authoritative Project repository.

## Secret safety

The release gate must never print or persist:

- `OPENROUTER_API_KEY`
- the one-time Runner registration token
- the long-lived Runner credential

Failure diagnostics may include durable Run/Issue/Review/Runner status, Execution Sessions, Run Events, candidate revision identifiers, and repository/test results only when they do not expose credentials.

## Fresh deployment smoke test

From a clean checkout and fresh PostgreSQL volume:

1. Start the documented Compose deployment.
2. Configure a Provider, Model Profile, and Agent with Engine + Model Profile.
3. Configure a local Git Project, create and assign an Issue, and verify a connected Runner is selected by the scheduler.
4. Complete a real Run through Review and approval and verify the accepted change is present in the Project repository.

Normal external Runner execution does not require Docker daemon access. Docker Runtime/Runtime Instance behavior remains legacy/internal managed-compute compatibility.

## Physical external-host validation

CI proves a real standalone `agent-runner` process across the production registration/WebSocket boundary, but it is not a physical remote host. Physical-host validation remains a manual operator check using `docs/external-runner-setup.md` and must be reported as manual rather than automated.

## PR evidence

The release PR should record the exact verification commands, relevant GitHub Actions runs, the allowlisted Provider/model used by the live test, and the manual physical-host result when performed. Never include credentials or Runner tokens in PR evidence.
